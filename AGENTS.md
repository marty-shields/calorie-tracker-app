# AGENTS.md — Calorie Tracker

Personal Android app (.NET 11 MAUI Blazor Hybrid). Setup: [docs/dev-setup-build.md](docs/dev-setup-build.md) ([Windows](docs/dev-setup-windows.md), [Linux](docs/dev-setup-linux.md)). E2E runs: [docs/e2e-tests.md](docs/e2e-tests.md). Release: [docs/release.md](docs/release.md). Screen behaviour: the design system's [screen pages](src/CalorieTracker.UI.Stories/Stories/Screens/) (BlazingStory). Work items and their acceptance criteria: GitHub issues.

## Commands
- Build: `dotnet build CalorieTracker.slnx` (warnings fail the build)
- Code style: `dotnet format CalorieTracker.slnx --verify-no-changes` (CI runs it; drop `--verify-no-changes` to apply the fixes)
- Test: `dotnet test tests/CalorieTracker.Core.Tests` and `dotnet test tests/CalorieTracker.UI.Tests`
- E2E (needs a device; a plain `dotnet test` skips them): build the App, then `dotnet test tests/CalorieTracker.E2E.Tests --filter "Category=smoke"`
- E2E without a device (Linux): `.github/scripts/e2e-local.sh "<filter for what you changed>"` boots an emulator, runs the filter, tears it down; exit 2 means skipped, so say the tests did not run ([details](docs/dev-setup-linux.md#throwaway-emulator-for-agents)). The full suite is CI-only (4 shards); one emulator can take a long time as the suite grows. The script refuses a broad filter, more than 15 scenarios or a run over 10 minutes; `E2E_ALLOW_BROAD=1` is the deliberate opt-in.
- Red emulator shard: read the job summary's `infra` or `test` verdict (`classify-shard-failure.sh`). Rerun the failed job once, and only on `infra`. On `test`, or when the rerun fails too, fix the cause instead ([rule](docs/e2e-tests.md#a-red-emulator-shard)).
- Story layout (needs Chrome and the stories running): `node .github/scripts/check-story-layout.mjs http://localhost:5056 <chrome> "Calorie Tracker/Components/" "Calorie Tracker/Screens/"` fails on clipped, overflowing or wrapping story content at the narrowest card; CI runs it as `story-layout`, and `data-wrap-ok` marks text allowed to wrap.
- README screenshots (needs Chrome and the stories running): `node .github/scripts/readme-screenshots.mjs http://localhost:5056 <chrome>` retakes every screenshot in the [README table](docs/dev-setup-build.md#readme-screenshots), light and dark; `--check` fails on any that no longer match their story. CI runs the check in `story-layout` and uploads retaken images as the `readme-screenshots` artifact when it fails.
- CI lint (needs `shellcheck`): `.github/scripts/lint-ci.sh` runs shellcheck over the scripts and actionlint over the workflows; CI runs it in `dev / build-and-test`.
- Docs: `python3 -I .github/scripts/check-docs.py` fails on a relative link or `#anchor` in a tracked `*.md` that doesn't resolve, or a README screenshot and its table row that don't match; CI runs it in `dev / build-and-test`.
- Food names: `python3 -I .github/scripts/check-food-names.py` fails on a seed food with no everyday name, a duplicate, an overlay that doesn't match the seed, or a name that breaks the [naming guide](src/CalorieTracker.Core/Seed/naming-guide.md); `--base <seed.json>` also fails on a changed `sourceId` or `originalName` (CI passes the base branch's seed on pull requests; by hand: `git show origin/main:src/CalorieTracker.Core/Seed/cofid-foods.json > /tmp/base.json`); CI runs it in `dev / build-and-test`.
- Shared UI kit: a general component or token (one another app could use) is added to app-ui-kit, not here; this repo holds the screens (`*Page`, `*View`), app-only components and the few tokens the kit lacks. `NoLocalKitCopiesTests` fails on a `.razor` under `src/CalorieTracker.UI` named like a kit component or a kit token declared in this app's `tokens.css` (the names come from `Shields.UI.Testing`'s `KitNames`), and `TokensOnlyCssTests`, `ContrastTests` and `TouchTargetTests` run its checks over this app's CSS. To try a kit change before it is released, build with `UseKitSource` as below, and do not commit the lock-file changes. The UI project takes `Shields.UI` (theme, tokens, base styles, `ThemePreference`) and the stories library takes `Shields.UI.Stories` (phone frame, theme switch, token and app icon sheets, `blazor-ui.css`) from the NuGet packages. To build against a checkout of the kit instead, pass `-p:UseKitSource=true -p:RestoreLockedMode=false` (needs `KitPath`, by default `../app-ui-kit` next to the repo; set `-p:KitPath=<folder>` otherwise, for instance from a worktree under `.claude/worktrees/`), e.g. `dotnet build src/CalorieTracker.UI -p:UseKitSource=true -p:RestoreLockedMode=false`; the lock files describe the package, so check `git status` afterwards and restore normally to put them back. The App's and the stories host's pages load the kit's `theme.js`, `tokens.css` and `base.css` before this app's `tokens.css`, which holds only tokens the kit lacks (plus temporary overrides marked with the issue that removes them).
- Design system: `dotnet run --project src/CalorieTracker.UI.Stories.Host` → http://localhost:5056 (the stories are the library `src/CalorieTracker.UI.Stories`; every title starts with `StoryTitles.Prefix`, `Calorie Tracker/`)

## How the code fits
- Projects: App → UI → Core; Stories (library) → UI; Stories.Host → Stories. `CalorieTracker.UI.Tests` reads the App's files because it can't reference it.
- Screens: a `*Page` calls services, a `*View` takes parameters. `StoryCoverageTests` requires a screen story for every `*View`.
- Navigation: the bottom bar is **Today** | a raised **+ Add** | **Trends** (`NavDestinations` feeding the kit's `BottomNav` through `NavScreen`; Add is an action, not a destination). There are no Foods or Scan tabs. Today (`DashboardPage`/`DashboardView`, whose code names are unchanged) is the start destination, so Android back leaves the app there and goes to Today from Trends (`/trends?period=week|month|year&from=yyyy-MM-dd`). Add opens `AddSheet` through `AddSheetHost` (shared by Today and Trends): meal chips with the meal `MealWindows.MealFor` gives for the time, **Search foods** and **Scan barcode**, and up to 3 "Usual for <meal>" rows (`UsualFoodsFeed`) added in one tap at the last amount, with Undo. Search and scan always add to a meal and a day (`/foods?meal=&date=`, `/scan?meal=&date=`; with no `meal` they use `MealWindows` and today); there is no browse-only values view, and a result opens Serving.
- Meal windows: `MealWindows` (Core, pure: the caller passes the local time) fixes breakfast 05:00–11:00, lunch 11:00–15:00, dinner 17:00–21:00 and snacks any time, with no setting. `MealFor` guesses the meal for Add (Snacks between and outside the windows); `StateFor` says Before, During, After or AnyTime. On Today a meal folds after its window and shows "Now" during it, only for today, recomputed when the day loads and when the app resumes, never live and never stored. A Debug-only `E2EClockSeam` lets E2E pin the time (not in Release; [e2e-tests.md](docs/e2e-tests.md#clock-seam)).
- Services return a status (such as `ReadResult<T>` or a result record), not exceptions.
- Every database call goes through `DatabaseGate` (`DatabaseGateTests`).
- Event ids: `CoreEvent` 1000–1999 (mostly a block of 100 per type; `ServingService` 1010, `FoodHistoryService` 1050, `FoodImportService` 1060, `FavouriteService` 1070 and `TrendsService` 1080 (1081–1086) sit in the 1000 block, `TargetService` has 1605–1607 for the target history in its 1600 block, and the online search 1520, online import 1540 and online notice 1550 are blocks of ten inside 1500), `UiEvent` 2000–4999 (a block of 100 per type; the Add sheet and the usual foods use 2301–2308 in the 2300 block, `TrendsPage` 2401–2403 in the 2400 block), `AppEvent` 5000–8999, the kit's `KitEvent` 9000–9999. `CoreEventTests` and `EventIdTests` fix the values and ranges.
- Components and namespaces: the kit's components (`Icon`, `AppButton`, `Snackbar`, `AppScreen`, `BottomNav` and the rest of `KitNames.Components`) live in the `Shields.UI` namespaces and log under the kit's `KitEvent` range, not `UiEvent`; this app's own components stay in `CalorieTracker.UI.Components`.
- Styling: tokens only, no literal colours or sizes (`TokensOnlyCssTests`, which uses the kit's `TokensOnlyCheck`).
- Logs hold no PII: ids, counts, events and non-personal data such as a scanned barcode are fine, personal data never is (obfuscate when needed; the food search is stricter and never logs its query or the barcodes it returns) (`Logging.feature`). Add a test that a new feature's log lines carry no PII.
- Docs: `ReadmeDocsTests` checks the README's screenshot table and Project layout.
- Upgrade check: `Upgrade.feature` and `UpgradeSeed.feature` save and check what the last release stored (the theme, the daily target with a back-dated earlier one for the target history, and one logged food that is also a favourite: it must stay in the diary, show its title and be found by search); the upgrade jobs skip until a `v*` tag exists.
- Servings: a food's servings are the rows of the `Serving` table the person adds (User rows, written by `ServingService`); nothing is read from a product about servings, and `FoodService.Offered` offers User rows only. A diary entry added by servings holds the `ServingId`. `Food` has no serving fields (schema step 16 dropped the `ServingLabel` and `ServingAmount` columns with the `FoodBarcode` table, step 18 deleted every Product and Pack row and dropped `ServingChecked`); `ServingSource.Product` and `Pack` stay as enum values only because stored data and the frozen steps 13 and 15 use them, and event 1308 is retired.
- Favourites: a favourite is a food the person marked, with no amount, stored as a row of the `Favourite` table keyed by food id (schema step 19; not a `Food` column, because seed upserts rewrite `Food` rows). `FavouriteService` adds, removes and lists them (statuses, never exceptions), and `FoodStore.DeleteMissingAsync` keeps every food with a `Favourite` row, so the seed clean-up never removes one.
- Target history: `TargetService.SaveAsync` and `ClearAsync` also write today's local-date row of the `TargetHistory` table (`EffectiveFrom` `yyyy-MM-dd`, `Kcal` null once cleared; schema step 20, which seeds `0001-01-01` from a target set at upgrade) in the same `DatabaseGate` call as the setting; `ForDateAsync` and `ForRangeAsync` give the target each day had (statuses, one read for a range). `AppSettings` stays the source of the current target.
- Trends: `TrendsService.GetAsync(from, to, today)` builds the figures of the Trends screen (`TrendsPage`/`TrendsView`, charts in `Components/Charts/`; its cards, tiles, legend and period stepper are the Shields.UI kit's `Card`, `StatTile`, `ChartLegend` and `PeriodStepper`) from one read of the range's entries and `TargetService.ForRangeAsync`. A past day is on target within ±10% of the target that day had (`TargetService` history, so changing the target never changes a past judgement), under below it and over above it; today and later days stay out of the averages. The bucket kind comes from the range length (a week or less none, up to 62 days weeks, longer months). A figure needs `TrendsService.MinDays` (3) logged past days (the on-target, under and over counts need 3 logged days that have a target), else the screen keeps its layout and says "Not enough data yet". Logs carry range lengths, counts and entry and food ids only.
- Food search: `FoodSearch` ranks in memory (`FoodRanker`: exact, prefix and bracket matches; a one-letter typo only when nothing else matches), groups the results (favourites, diary, common, branded) and, before you type, lists the favourites and suggests foods from `FoodHistoryService`. `FoodDisplay` makes a food's title, brand line and pack for every screen. Search has no type filter. `FoodImportService` is the one way a looked-up product is stored (barcode and product in, the food it ended on and a status out; nothing in it knows about scanning, so a later search by name can call it): idempotent, never throws, and a product with the same brand, name (size words ignored), unit and nutrients (`ProductMatch`, 2% or 0.1) gets its barcode added to the stored food (one `Barcode` row for each barcode, with its pack) instead of a food of its own. A scan or its background refresh stores the product's name, brands, generic name, pack size and extra nutrients; no images are loaded. `OnlineFoodSearch` is the one text search of Open Food Facts (Search-a-licious, `IOnlineFoodSearch`): it sends only when the person taps "Search online" (a button pinned in the screen's bottom bar while text is typed and the search has not run for it; the spinner and results stay in the list), never on a keystroke or page load, at most once every 2 seconds, with the typed text and the device country filter (`OffCountries`, generated from Open Food Facts' country list, GB mapped to the UK tag) and nothing else, keeps finished searches in memory for the session, cleans the hits (no barcode, name, unit or nutrition: skipped; same name, pack and per-100 values: collapsed; at most 20) and logs counts only. A tap on a result goes through `OnlineFoodImport` (the barcode lookup, then `FoodImportService`); nothing else stores a search result.
- New screen: it needs a `*Page`, a `*View`, a story per state, a docs page under `Stories/Screens/`, an entry in `ScreenStates` and its E2E scenarios.

## Rules
- Ask about any ambiguity.
- No new packages without approval.
- XML comments only when they add something the name and type don't (a unit, a range, what null means, an order, a why). Component parameters are the exception. Never restate the name. Build warnings no longer ask for them, and CI's `check-filler-comments.py` fails a `<summary>` or `<param>` that only restates the name (a real exception gets `/// <!-- filler-ok: why -->`).
- Interfaces only where something else implements them, such as a test fake or the stories site. No interface for a single implementation nothing swaps.
- Commit on a branch, push it and open a ready (non-draft) PR when the work is done, so all CI runs (a draft skips the heavy jobs). Merge into `main` only when the user says to.
- Epics: a task of an epic issue gets a `task/<epic>-<id>` branch and a PR into the epic's `epic/<name>` branch, not `main`. You may squash-merge that PR yourself once its checks are green, a verifier other than the author has run every acceptance criterion on the issue and every review finding is fixed. Put open questions in the PR, then add them to the epic PR description when you merge. Never merge an epic PR ([how](docs/epics.md)).
- PR titles are Conventional Commits with exactly one `semver:major|minor|patch` label (CI checks both).
- A PR that changes the UI includes screenshots of the changed screens, posted as a PR comment or in the body, before it is marked ready.
- A PR that changes how a screen in the README looks (its markup, CSS, tokens, or the sample data its story shows) retakes the README screenshots with `readme-screenshots.mjs` and commits them in the same PR. Run `--check` before marking it ready; never leave them stale for later.
